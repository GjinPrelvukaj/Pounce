# Gate M3 — the query layer, measured at 1M rows

**Date:** 2026-08-24
**Host:** Apple M5, macOS 27.0. Dev laptop, not a controlled rig.
**Harness:** `crates/pounce-store/tests/gate_m3.rs` — asserts the thresholds
rather than printing them, so a regression fails a test rather than a reading.

```bash
cargo test --release -p pounce-store --test gate_m3 -- --ignored --nocapture
```

**Seeded, not crawled.** The probe's real 500k and 1M databases no longer exist
and re-crawling them is hours. 1,000,000 pages with a crawl-shaped status mix
(94% 200, 5% 404, 2% 500), 94% HTML, 10% noindex, two thirds carrying an issue.
Seeding took 26 s, the read-path indices 6.7 s, and the file is 1,030 MB.

## 3. What the 1M run found that 200k had hidden

**Equality and range are different queries.** At 200k, `depth <= 2` sorted by
word count looked like any other pair. At 1M it is 480 ms, because a composite
`(depth, word_count)` index can only return rows in word-count order when the
`depth` constraint is an **equality**. With a range, SQLite walks the sort index
and fetches each row to test the filter:

| depth filter, sorted by size | |
|---|---:|
| `depth = 2`, no composite (before) | 282 ms |
| `depth = 2`, composite `(depth, size)` | **1.6 ms** |
| `depth <= 2`, composite present or not | 101 ms |

So support is now declared per `(FilterShape, sort)`, not per `(FilterKind,
sort)` — `status = 200` and `status >= 400` are the same column and get
different answers. `FilterShape::Range` is allowed only with the sort columns
measured safe for a per-row lookup: url 72, status 34, depth 26, size 101,
title 42 ms. It is refused with `word_count` (480 ms) and `elapsed_ms` (427 ms),
which are the low-cardinality columns where every skipped row is a table lookup
landing somewhere else in the file.

The composite set grew from 20 to **26** as a result: all seven sort columns for
`status`, `kind`, `noindex` and `depth`, so their equality case never falls back.
`word_count` gets none — nobody filters for an exact word count, and its range
case cannot use one anyway. Ceiling is 30, asserted.

**The issue overview was the slowest thing in the layer**, at 564 ms, and it is
not even a gate item. Two temp B-trees: one for `GROUP BY rule_id, severity` and
one for `count(DISTINCT url)`.

| | |
|---|---:|
| As written | 564 ms |
| `+ index (rule_id, severity, url)` | 102 ms for the grouped query |
| `+ distinct page ids instead of distinct URLs` | 10 ms for the global count |
| **Total now** | **158 ms** |

Counting distinct *page ids* needs care: `count(DISTINCT)` ignores NULLs, and a
finding whose subject never became a page has a NULL `page_id`. Those are
counted by a second query, or a crawl's redirect loops would be missing from its
own headline number.

## 4. Memory

12 MB resident for a 5-row window and 12 MB for a 1,000-row window, on a 1M-row
database — the 200× change `MAX_WINDOW` allows. The dataset is never
materialised, which is the whole architecture in one measurement.

## 5. A live writer

Untested in the probe, and the state the app is in for an entire crawl. With a
write batch **held open**, a reader on a second connection returned its window
in 13.3 ms. WAL does what it was chosen for.

## 6. The weakest number, and what would fix it

`has_issue` is 180–220 ms across its supported sorts — passing, with the least
headroom of anything here. It compiles to `EXISTS` against `issues_page`, one
lookup per row the offset skips, and no index on `pages` can serve it.

The fix, if it is ever wanted, is a denormalised flag on `pages`, which turns it
into an equality filter and puts it with the 17 ms pairs. **Not taken now**: it
is a second copy of a fact `issues` already holds, which is exactly what T3.0
rejected `row_view` for, and it would put an indexed `UPDATE` on the crawl's hot
path. Revisit if the number regresses or the filter proves as common as expected.

`has_issue` sorted by `word_count` measured 275 ms — inside the gate but not by
enough to promise, so it is refused rather than offered.

## 7. What is still not established

- **Seeded data, not a crawl.** The status mix is realistic and stated; URL
  shapes are uniform in a way a real site is not.
- **One window size and one offset depth** per pair — half way in, which is the
  worst case for `OFFSET`.
- **No competitor comparison.** This measures the gate, not the market.
- **macOS only.** CI runs the correctness tests on all three platforms, but
  these timings are one machine's.
