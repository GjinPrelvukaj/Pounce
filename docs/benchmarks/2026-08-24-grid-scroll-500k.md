# T4.9 — the grid at 500,000 rows

**Date:** 2026-08-24
**Host:** Apple M5, macOS 27.0, 60 Hz display. Dev laptop, not a controlled rig.
**Build:** production (`tauri build --no-bundle`), which is the only build that
serves the bundled frontend and the release-compiled engine.
**Data:** 500,000 seeded rows, 681 MB, from
`cargo test -p pounce-store --test gate_m3 seed_a_store` with a crawl-shaped
status mix.

---

## 1. What had to be true

PLAN.md's done-condition for T4.9: *"scrolling 500k rows stays at 60fps and
memory stays flat"*. That is the visible half of the spec's central claim — the
UI never receives the dataset — so it is measured rather than asserted.

## 2. Result

| | median | p95 | worst | dropped frames |
|---|---:|---:|---:|---:|
| **steady scroll** — 3 rows per frame, a trackpad flick | 17.0 ms | 18.0 ms | 19 ms | **0.0%** |
| **fling** — all 500,000 rows in 10 s, a scrollbar drag end to end | 17.0 ms | 23.0 ms | 71 ms | **2.4%** |

**Memory: 99–105 MB, flat across the whole run**, sampled twice a second from
outside the process. The file is 681 MB; the window holds at most 12 windows of
200 rows.

## 3. How the frames were counted, and one wrong turn

The first version of this harness reported "57% of frames slower than 16.7 ms"
and looked like a failure. It was measuring nothing: **at a locked 60 Hz vsync,
every healthy frame is one frame interval**, so a threshold at 16.7 ms counts
good frames as bad. The harness now samples an idle baseline first — 17.0 ms
here, confirming a 60 Hz display — and a *dropped* frame is one that took more
than 1.5× that.

Read that way: steady scrolling drops nothing, and dragging the scrollbar across
half a million rows drops 2.4% with one hitch at 71 ms. A fling asks for a
complete row replacement plus a window fetch on every frame, so it is the
pessimistic case by construction, not the common one.

**The debug build measures something else.** The same harness against
`cargo run` gave p95 37 ms and a worst of 61 ms, because every window fetch goes
through a debug-compiled SQLite. Grid numbers from a debug build are not
numbers.

## 4. What keeps memory flat

`MAX_WINDOWS = 12` in `ui/src/Grid.tsx` — 2,400 rows, a few hundred kilobytes.
Windows outside that are evicted by distance from the viewport, so scrolling
back up does not re-fetch what is directly above. Without eviction the cache
grows to the whole dataset on a long scroll, and the app would look correct
until someone opened a real crawl. That constant is the invariant in the one
place it could quietly stop being true.

## 5. TanStack Table is not used, and why

PLAN.md said "TanStack Table + Virtual". `react-virtual` earns its place —
measurement, overscan and scroll maths are real work. `react-table` did not:
sorting, filtering and pagination are all server-side in this design, and the
row model only ever holds the visible window, so the library would contribute
column descriptors and a render helper — about twelve lines — in exchange for an
API that changed shape between its last two majors (v9 renamed
`useReactTable`/`getCoreRowModel`). Columns are now a plain array of
`{ key, header, width, render }`, which is also what T4.10's column picker
needs.

An earlier draft *did* use it, and its cell lookup was a `.find()` per cell
inside the render loop — O(visible²) work on every scroll frame, in the one
component whose budget is 16 ms.

## 6. What is not established

- **One machine, one display.** 60 Hz; a 120 Hz panel halves the budget and has
  not been measured.
- **Unfiltered, sorted by URL.** A filtered view changes which index serves the
  window; T3.2's declared pairs are all 11–20 ms at 1M, so the fetch is not
  expected to dominate, but this run does not prove it.
- **No concurrent crawl.** The grid is usable during a crawl by design, and a
  live writer competing with these reads is untested here.
- **Not automated.** The harness was a temporary patch, not a committed test —
  a repeatable version needs a driver for the real webview, which does not exist
  in this project yet.
