# Pounce at scale — 100k and 500k

**Date:** 2026-08-21
**Host:** Apple M5, macOS 27.0, rustc 1.97.1, `--release`. Dev laptop, not a controlled rig.
**Command:** `bench-runner --pages {100000,500000} --seed 42 --tool 'pounce=…'`
**Purpose:** the two Gate M1 items that need no competitor.

---

## 1. Gate items — both pass

**100k fixture crawl, no lost or duplicated URLs — PASS.** Three consecutive runs,
each: **100,001 pages, 100,001 distinct URLs, 0 frontier entries left pending,
0 failures, every status 200.** 2,799,795 link edges. Verified with
`count(*)` / `count(DISTINCT url)` and a `frontier LEFT JOIN pages` for pending,
not inferred from the runner.

**Peak RSS under 400 MB at 500k — PASS, at 228 MB.** 500,001 pages, 500,001
distinct, 0 pending, 0 failures, 13,999,791 links. Sampled once a minute during
the run, resident memory sat flat between **144 and 174 MB** while the database
grew from 3.4 GB to 4.7 GB; 228 MB is the peak the runner caught, presumably
during a batch commit.

**Memory is genuinely flat, and that is the invariant working.** RSS rose 28 → 64
→ 228 MB across a 50× increase in crawl size while the on-disk database went to
4.7 GB. Nothing accumulates in memory proportional to crawl size.

## 2. The finding: throughput degrades badly with scale

| Fixture | Pages | Links | Wall | **URLs/s** | Peak RSS | rows/s (pages+links) |
|---|---:|---:|---:|---:|---:|---:|
| 10k | 10,001 | ~279k | 2.71 s | **3,690** | 28 MB | 106,642 |
| 100k | 100,001 | 2,799,795 | 66.1 s | **1,513** | 64 MB | 43,870 |
| 500k | 500,001 | 13,999,791 | 1,391.5 s | **359** | 228 MB | 10,420 |

**From 100k to 500k: 5× the pages, 21.1× the wall time.** Exactly quadratic would
be 25×. This is not "more rows take longer" — **row throughput itself collapses
10×**, from 107k rows/s to 10.4k. Each row costs more as the crawl grows.

Link count is a clean 28 per page at every scale, so the work per page is
constant. The slowdown is entirely in how long that constant work takes.

### Hypothesis — not yet profiled

Text-keyed B-tree indices that grow with the crawl, taking randomly-ordered URL
keys, so nearly every insert lands on a cold page:

1. **`links_target ON links (target_url)`** — a full `TEXT` index over 14M rows
   at 500k. The largest structure in the file and the prime suspect.
2. **`frontier`** — `WITHOUT ROWID`, `TEXT PRIMARY KEY`, plus
   `frontier_order (depth, url)`. Takes one upsert per discovered link, so ~14M
   at 500k.
3. `pages.url` unique index — 500k entries, an order of magnitude smaller.

**The experiment that would settle it:** re-run 500k with `links_target` dropped.
If wall time falls back toward linear, the index is the cost and the fix is to
build it after the crawl rather than maintain it during one. Until that is run,
the above is arithmetic and inference, not a diagnosis.

### Why this matters beyond M1

Extrapolating the observed scaling to **M9's gate — a 10M-URL crawl** — gives
something between 40 and 150 hours. M9 is not reachable on this curve. The fix
belongs before M9 and probably before M5, since the published benchmark should
not describe a crawler that gets slower the more it is asked to do.

## 3. This supplies the number the store benchmark said it could not

[`2026-08-21-store-insert-throughput.md`](2026-08-21-store-insert-throughput.md)
first concluded "the writer is not the bottleneck" from 95.7k rows/s at batch
500. T1.14/T1.15 already superseded that: with link rows counted, a fixture page
expands to ~22 SQL rows, and at 4.45k pages/s the writer sits below the fixture
server's ~17k req/s ceiling, so **SQLite bounds an unrestricted local crawl.**

That document's remaining caveat is the one this measurement answers:

> **Empty database.** … A 1M-page crawl pays more per row as those indices
> deepen. **This is not a 1M-page number.**

**Here is the number.** At 500k, with indices holding 500k page keys and 14M
link-target keys, the same writer sustains **10.4k rows/s counting pages and
links alone** — and that is an undercount, since frontier rows land too. Against
97.7k rows/s on an empty database that is a drop of at least 9×, and it is
caused by index depth, exactly as that caveat predicted.

## 4. What is still not established

- **Single run at 500k.** No median, no spread. The 100k figure is a median of three.
- **Not profiled.** §2's hypothesis is inference from row counts and index shapes.
- **Localhost.** A real crawl is bounded by the target server, and at 359 URL/s
  a polite crawler is nowhere near that bound — which is the honest reading:
  this degradation may be invisible on a real site and is still a defect.
- **Competitor comparison is unaffected.** FreeCrawl was measured at 10k, where
  Pounce is fastest. A fair 100k head-to-head has not been run, and Pounce's
  advantage there will be smaller than 49×.
