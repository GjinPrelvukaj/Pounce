## Table at 500k rows

`/tmp/big.pounce`, 500,000 pages seeded through `seed_a_store_for_the_app`
(10.7 s to seed, 5.3 s to build the read-path indices; 681 MB on disk).

Method, following the rule written into `CLAUDE.md` after the first attempt got
it wrong: **a rAF delta is one frame interval, not a latency.** At a locked
60 Hz every healthy frame measures ~16.7 ms, so "slower than 16.7 ms" counts
good frames as bad. An idle baseline is sampled first (1.5 s), then the grid is
scrolled 40 px per frame for 6 s and frames slower than 1.5× the baseline are
counted as dropped.

```
base 17.0 ms · frames 360 · dropped 0 (0.00%) · worst 19.0 ms · scrollTop 14,400
```

Peak RSS over the run: **79–116 MB** across three runs, on a 681 MB file. The
spread is the webview's own allocation, not the row cache — `MAX_WINDOWS` caps
that at 2,400 rows.

## Cold start

`POUNCE_STARTUP=1` prints the time from process entry to the webview's first
page-load completing. Thirteen launches:

```
257 261 264 266 268 272 279 282 283 285 337 369 470 ms
```

Median **272 ms**, and the 470 ms outlier is the first launch after a build,
with the 18 MB binary not yet in the page cache. Every warm launch is under
300 ms.

## Both themes

Production build, the ritecoach crawl open, dark and light captured from the
window itself. `npm run check:contrast` passes every text tier against its
ground in both themes, which is the part a screenshot cannot check.

## What is not closed, and why

**"Crawl a real site start to finish without touching a terminal."** This
session was instructed not to crawl the owner's site, and reaching for an
unrelated third-party site to satisfy a checkbox is not a decision to take
unattended. The flow was exercised end to end against the local fixture site
(3,000 pages, 40 ms delay): New crawl → form → start → live progress strip →
results filling during the crawl → completion, with the grid and the issue rail
climbing throughout.

Two caveats a human pass would remove:

1. It was driven by a temporary in-app harness, because this session has no
   Accessibility grant and cannot click the window. Every control was verified
   individually the same way, but nobody has yet used the app with a mouse.
2. The fixture is a local HTTP server. It exercises the crawler, the store, the
   audit rules and the whole interface, but not DNS, TLS, redirects across
   hosts, robots.txt on a real server, or a site that rate-limits.

**This is the one gate item that needs the owner.** Everything it depends on is
built and measured; what is missing is a person, a mouse, and a site they are
happy to crawl.
