01

The landscape has changed

Twelve months ago "free Screaming Frog alternative" was an open lane. It isn't now. Any plan that doesn't start here is fiction.

Three projects already ship free, unlimited-URL, cross-platform crawlers. Two of them are open source under permissive licenses — Pounce is not, and does not compete on that axis. One of them — FreeCrawl — already has disk-backed SQLite storage, a headless CLI, 200+ checks, GSC and GA4 integrations, and an MCP server. Matching that feature list is not a strategy.

The gap that's actually left

Not one of them is natively compiled. Electron ships a browser to render a table. Python's GIL fights its own crawler. Java needs a JVM and a heap flag. Every incumbent pays a runtime tax on the two things a crawler does most — parse HTML and hold a large result set in memory.

That is a real, structural, hard-to-copy advantage, and it is the only one still available. So it has to be the whole pitch.

02

Positioning

One sentence, and everything in the project is downstream of it:

Pounce crawls faster, on less memory, from a smaller binary than anything else — and every claim ships with a reproducible benchmark.

Three consequences follow, and they are not optional:

  • Benchmarks are a feature, not marketing. The benchmark harness is built in Phase 0, before the GUI. If you can't measure it on day one, you can't claim it on day ninety.
  • Feature parity is explicitly not the goal. FreeCrawl has 200+ checks. Pounce v0.1 caps at 30, and a test fails if a thirty-first is registered. Each one is fast, correct, documented, and ships with a fixture that triggers it and one that does not. Racing a feature list you're behind on is how solo projects die.
  • Every design tradeoff resolves toward speed. When "nicer UX" and "faster crawl" conflict, faster wins, and the UX gets solved a different way.
Honest risk

Speed is a real advantage, but it may not be one users feel. Most people crawl sites under 50k URLs, where every tool finishes in a couple of minutes. Your benchmarks need to lead with the numbers people do feel: cold-start time, memory on a big crawl, UI responsiveness while sorting 500k rows, and how far you get before the competitor's app becomes unusable.

03

Namedecided

Criteria, in order: short enough to type as a CLI verb, spider-adjacent without being cute, unclaimed in the SEO and Rust namespaces, and pronounceable by a non-English speaker reading it off a README.

Pounce was chosen and the shortlist below is kept as the record, not as an open question.

Pounce Chosen. Six letters, a verb, and literally what jumping spiders do. Reads as speed before it reads as arachnid, which matches the positioning exactly. pounce crawl example.com is a good command. Clean in the SEO namespace.
Spinneret The organ a spider extrudes silk from. Technical, precise, unmistakably on-theme, and almost certainly unclaimed. Costs you three extra syllables and some typing.
Skitter The most crawl-evocative of the set — but taken. An Elixir distributed-stream framework and an old jQuery slider both own the name. Not fatal in a different domain, muddies search forever.
Weft The crossing thread in weaving. Four letters, elegant, quiet. Says nothing about speed and nothing about SEO — a name you'd have to spend years teaching.
What the namespace check found

pounce and pounce-cli are both taken on crates.io, by an unrelated chess engine. Every other pounce-* name is free. This turned out not to matter: the project is closed source and every crate is publish = false, so nothing goes to crates.io at all. Should a published CLI ever be wanted, it can ship as pounce-seo while installing a binary named pounce.

The design direction is measurement instrument — oscilloscope, not dashboard.

The product's entire claim is a number, so the identity should look like something that produces trustworthy numbers: warm graphite housing, a single cold luminous trace, hairline gridlines, tabular figures everywhere. This page is built in it.

The app is not built in this

The identity below is the 19 August exploration, and this page still wears it. The application went a different way and PRODUCT.md § Brand Commitments is now authoritative: the accent is violet (#6A4DF4) over warm neutrals — paper and charcoal, not near-black — with Inter everywhere and JetBrains Mono reserved for text read character by character. Severity — deliberately outside the brand

A crawler UI is 90% severity states. If the brand colour sat in the red–amber–green band it would collide with meaning on every screen. Cyan was chosen precisely because it leaves that band untouched — and violet, which replaced it, clears the band by an even wider margin. This is the one part of the identity that is a functional requirement rather than a preference, and it is the reason both palettes work.

The app additionally never encodes a severity by colour alone: every one is drawn with an icon and a word, so the states remain separable without hue. npm run check:contrast fails the build if any text tier drops below WCAG AA in either theme.

The shipped rule is narrower than this one, and deliberately. Monospace is only for text a person reads character by character — a URL, a path, a canonical. Mark

An orb web reduced to its radial threads, with the right-hand threads brightened so they read as motion lines. The centre node is the crawler. It works at 16px as a favicon, mono-colours cleanly for a terminal splash, and never needs to be drawn as a literal spider — which keeps it out of Halloween-clipart territory.

Voice

  • Numbers over adjectives. Not "blazingly fast" — "412 URLs/sec on a 4-core laptop, here's the harness."
  • Never trash the competition by name. Publish the benchmark, include them in it, let the table talk.
  • Say what it can't do. The README should have a "what this doesn't do yet" section above the fold. It buys more trust than any feature list.

Architecture

A Cargo workspace of small crates, each independently testable. The GUI is one consumer of the engine, never the owner of it.

pounce/
├─ crates/
│  ├─ pounce-core      orchestrator, frontier, scheduler, crawl lifecycle
│  ├─ pounce-http      fetch pool, retries, redirect chains, robots.txt, rate limits
│  ├─ pounce-parse     lol_html extraction → PageRecord (title, meta, links, hreflang…)
│  ├─ pounce-store     SQLite schema, batched writer, query API, resume state
│  ├─ pounce-audit     rule registry; each check is one testable unit
│  ├─ pounce-export    CSV / JSON streamed · XLSX / PDF / DOCX reports
│  ├─ pounce-run       the crawl runner: frontier loop, image pass, lifecycle wiring
│  ├─ pounce-bench     benchmark harness + fixture site (Phase 0)
│  ├─ pounce-cli       headless binary, CI exit codes
│  └─ pounce-app       Tauri commands + events (thin)
└─ ui/                  React + TanStack, virtualised grid

The decision that makes or breaks it

Never send the dataset to the UI

The obvious design — crawl into memory, serialise results over Tauri IPC, render in React — falls apart somewhere around 100k rows and will make a Rust app feel slower than the Electron one. That failure is the single most likely way this project dies.

Instead the UI holds no crawl data at all. It sends queries; SQLite answers with only the visible window.

// The UI asks for what's on screen. Nothing more, ever.
#[tauri::command]
async fn query_rows(
    crawl: CrawlId,
    filter: FilterSpec,      // compiled to a WHERE clause
    sort: SortSpec,          // indexed columns only
    offset: u32, limit: u32, // limit is ~200, the viewport
) -> Result<Page<RowView>>

// Progress arrives on a channel, throttled to 10 Hz —
// not one event per crawled URL.
#[tauri::command]
async fn subscribe_progress(ch: Channel<CrawlProgress>)

Sorting and filtering become SQL against indexed columns, which SQLite does in milliseconds on millions of rows. Scroll position maps to OFFSET. Memory stays flat regardless of crawl size, and the app stays responsive mid-crawl because reads and writes are separated by WAL.

Crawl pipeline

Frontier (priority queue, deduped) → fetch pool (N workers, per-host rate limits) → parse (streaming, on a blocking thread pool) → batched writer (transactions of ~500 records) → audit rules (run incrementally, not at the end). Backpressure via bounded channels between each stage, so a slow disk throttles the fetchers instead of ballooning memory.

Politeness, non-negotiable

robots.txt honoured by default, per-host concurrency caps, configurable delay, honest identifiable user-agent with a URL to the project, and Retry-After respected. A fast crawler that gets its users IP-banned is a liability. Ship the safe defaults and make aggression opt-in and clearly labelled.

08

Roadmap

Phases are sequential because each depends on the one before it — Phase 0 exists so that every later claim is measurable.

0.0 and 0.1 are done, and 0.1 took closer to the top of its range than the bottom. The engine, the audit rules, the query layer and the desktop app all shipped; what is left of 0.1 is packaging — signing, notarisation, and one gate item that needs a person and a mouse.

0.02 weeks

Benchmark harness firstdone

A fixture site generator (axum) producing 100k pages with realistic link density, plus pathological cases: redirect loops, 30s responses, 5MB pages, malformed markup, robots edge cases. Criterion benches for parse throughput. A runner that measures URLs/sec, peak RSS, and wall time for Pounce and each competitor identically. Nothing else gets built until this works.

0.110–14 weeks

MVP — crawl, audit, table, exportpackaging left

The scope above. Ships with the first published benchmark and a README that names what's missing. Built and measured; the remaining work is signed installers and a same-day head-to-head, not features.

0.26 weeks

CLI and CInext

pounce crawl --config pounce.toml --fail-on critical, JSON report output, meaningful exit codes, and a published GitHub Action. This is the "by developers, for developers" promise made real, and it's the thing no GUI-first competitor does well.

0.38 weeks

JavaScript rendering

chromiumoxide over CDP, as an opt-in per-crawl mode with its own concurrency budget. Detects installed Chrome rather than bundling one, so the binary stays small for the people who don't need it.

0.46 weeks

Custom extraction & crawl diffing

CSS/XPath/regex extractors, XML sitemap generation, and crawl-to-crawl comparison — "what changed since the last deploy" is the feature that turns a one-off audit tool into something opened weekly.

0.58 weeks

Integrations & scale

Search Console and GA4 joins, log file ingestion, link graph visualisation, and the push from 1M to 10M URLs per crawl.

1.0—

Rule SDK

Custom audit rules as WASM modules or embedded scripting. Developers writing and sharing their own checks is the endgame — it's the one thing that compounds, and it's where a free open tool beats a commercial one permanently.

10

Testing

  • Golden-file parser tests. A corpus of real-world HTML — including badly broken markup — with committed expected PageRecord output. Parser regressions are the highest-consequence bug class here, because they silently produce wrong audits.
  • The fixture site is the integration test. The same axum server built for benchmarking serves deterministic pathological cases. Crawl it, assert the exact resulting graph.
  • One test per audit rule. Every rule ships with a fixture that triggers it and one that doesn't. Non-negotiable — this is what keeps rule count from becoming rule debt.
  • Property tests on URL normalisation. Relative resolution, trailing slashes, case, ports, punycode, fragments, session IDs. This is where crawlers quietly break and loop forever.
  • Criterion benches in CI with regression thresholds. If throughput drops 10%, the build fails. When speed is the product, a perf regression is a broken build.

Projectreversed

This section was reversed on 28 August 2026

The plan assumed open source, and the project is not. Pounce is proprietary and closed source: LICENSE is all-rights-reserved, every crate carries publish = false and no license field, and nothing goes to crates.io. A contributor guide and a Sponsors page are furniture for a project that takes contributions, and this one does not — both were cut rather than written.

Free did not change. Closed source and free are different axes, and only one of them moved.

Licence

All rights reserved. The dual MIT / Apache-2.0 pairing below the fold of every Rust project buys contributor goodwill, and goodwill is worth what it costs only if contributions are wanted. Here the differentiator is a compiled engine and a measured benchmark, neither of which a licence protects or exposes.

Repository

Monorepo. README leading with the benchmark table and a "what this doesn't do yet" section — whose gap list names exactly what the app's own "not checked in this version" panel names, because those two disagreeing is the failure that disclosure exists to prevent. ARCHITECTURE.md explains the query-don't-dump decision with the measured number beside each choice. Conventional commits; a GitHub Actions matrix for the three platforms, written and not yet run.

Sustainability

No paid tier, no telemetry, no account — stated in the README as a promise about the product rather than as a donation button. That is the strongest trust signal available to an audience that has watched a dozen free dev tools get acquired and enshittified, and it survives the licence change intact.

Distribution

GitHub Releases, once the builds are signed. Package managers follow. The cargo install path is gone with the licence: the crates are unpublished, and pounce and pounce-cli were taken on crates.io anyway.

What is actually left

The three actions this section originally listed — clear the name, build the benchmark harness, spike the storage layer — are all done, and the third one answered the question it was set: the query layer returns a filtered, sorted, paginated window of a million rows in 138 ms.

Nothing below is a feature. It is the difference between working software and a release someone else can install.

  1. Sign and notarise. needs the owner An Apple Developer account and a Windows certificate. Until this exists the installers warn on both platforms, and it is the long pole — notarisation is the multi-day surprise, and everything downstream of it is packaging.
  2. Re-take the head-to-head. Our half is measured. The competitor's half is eight days stale and stale in our favour, which is the direction that costs credibility rather than saving face. Both halves, one machine, one day, competitors' timeouts and errors published rather than dropped.
  3. Decide the public identity. a brand decision This page and the application no longer look like the same product. The landing page cannot be built until someone says which one is right — and building it in the wrong one is worse than not building it.
  4. Crawl a real site, start to finish, without touching a terminal. needs a person The last open item on the desktop gate. Exercised end to end against the local fixture; it needs a human, a mouse, and a site they are happy to crawl.
The honest version, two weeks later

The premise held. The performance gap is real and it is measured, the scope stayed narrow enough that the rule cap is enforced by a test rather than by willpower, and the architecture's load-bearing assumption — never send the dataset to the UI — survived contact with a million rows.

What the plan got wrong was the licence, and what it under-estimated was the last ten percent. Four of the remaining items need a human decision, an account, or a mouse. None of them need more code.
