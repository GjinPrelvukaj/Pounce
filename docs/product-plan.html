01

The landscape has changed

Twelve months ago "free Screaming Frog alternative" was an open lane. It isn't now. Any plan that doesn't start here is fiction.

Three projects already ship free, unlimited-URL, cross-platform crawlers. Two of them are open source under permissive licenses. One of them — FreeCrawl — already has disk-backed SQLite storage, a headless CLI, 200+ checks, GSC and GA4 integrations, and an MCP server. Matching that feature list is not a strategy.

The gap that's actually left

Not one of them is natively compiled. Electron ships a browser to render a table. Python's GIL fights its own crawler. Java needs a JVM and a heap flag. Every incumbent pays a runtime tax on the two things a crawler does most — parse HTML and hold a large result set in memory.

That is a real, structural, hard-to-copy advantage, and it is the only one still available. So it has to be the whole pitch.

02

Positioning

One sentence, and everything in the project is downstream of it:

Pounce crawls faster, on less memory, from a smaller binary than anything else — and every claim ships with a reproducible benchmark.

Three consequences follow, and they are not optional:

  • Benchmarks are a feature, not marketing. The benchmark harness is built in Phase 0, before the GUI. If you can't measure it on day one, you can't claim it on day ninety.
  • Feature parity is explicitly not the goal. FreeCrawl has 200+ checks. Pounce v1.0 will have maybe 60, and each one will be fast, correct, and documented. Racing a feature list you're behind on is how solo projects die.
  • Every design tradeoff resolves toward speed. When "nicer UX" and "faster crawl" conflict, faster wins, and the UX gets solved a different way.
Honest risk

Speed is a real advantage, but it may not be one users feel. Most people crawl sites under 50k URLs, where every tool finishes in a couple of minutes. Your benchmarks need to lead with the numbers people do feel: cold-start time, memory on a big crawl, UI responsiveness while sorting 500k rows, and how far you get before the competitor's app becomes unusable.

Name

Criteria, in order: short enough to type as a CLI verb, spider-adjacent without being cute, unclaimed in the SEO and Rust namespaces, and pronounceable by a non-English speaker reading it off a README.

Pounce Recommendation. Six letters, a verb, and literally what jumping spiders do. Reads as speed before it reads as arachnid, which matches the positioning exactly. pounce crawl example.com is a good command. Clean in the SEO namespace.
Spinneret The organ a spider extrudes silk from. Technical, precise, unmistakably on-theme, and almost certainly unclaimed. Costs you three extra syllables and some typing.
Skitter The most crawl-evocative of the set — but taken. An Elixir distributed-stream framework and an old jQuery slider both own the name. Not fatal in a different domain, muddies search forever.
Weft The crossing thread in weaving. Four letters, elegant, quiet. Says nothing about speed and nothing about SEO — a name you'd have to spend years teaching.
Verify before committing

Check crates.io/crates/pounce, the npm and PyPI names, GitHub org availability, and pounce.dev / pounce.sh. Do this before you write a line of code — renaming a project after the first release is far more painful than it sounds.

Voice

  • Numbers over adjectives. Not "blazingly fast" — "412 URLs/sec on a 4-core laptop, here's the harness."
  • Never trash the competition by name. Publish the benchmark, include them in it, let the table talk.
  • Say what it can't do. The README should have a "what this doesn't do yet" section above the fold. It buys more trust than any feature list.

06

Architecture

A Cargo workspace of small crates, each independently testable. The GUI is one consumer of the engine, never the owner of it.

pounce/
├─ crates/
│  ├─ pounce-core      orchestrator, frontier, scheduler, crawl lifecycle
│  ├─ pounce-http      fetch pool, retries, redirect chains, robots.txt, rate limits
│  ├─ pounce-parse     lol_html extraction → PageRecord (title, meta, links, hreflang…)
│  ├─ pounce-store     SQLite schema, batched writer, query API, resume state
│  ├─ pounce-audit     rule registry; each check is one testable unit
│  ├─ pounce-export    CSV / JSON / XLSX / sitemap XML
│  ├─ pounce-bench     benchmark harness + fixture site (Phase 0)
│  ├─ pounce-cli       headless binary, CI exit codes
│  └─ pounce-app       Tauri commands + events (thin)
└─ ui/                  React + TanStack, virtualised grid

The decision that makes or breaks it

Never send the dataset to the UI

The obvious design — crawl into memory, serialise results over Tauri IPC, render in React — falls apart somewhere around 100k rows and will make a Rust app feel slower than the Electron one. That failure is the single most likely way this project dies.

Instead the UI holds no crawl data at all. It sends queries; SQLite answers with only the visible window.

// The UI asks for what's on screen. Nothing more, ever.
#[tauri::command]
async fn query_rows(
    crawl: CrawlId,
    filter: FilterSpec,      // compiled to a WHERE clause
    sort: SortSpec,          // indexed columns only
    offset: u32, limit: u32, // limit is ~200, the viewport
) -> Result<Page<RowView>>

// Progress arrives on a channel, throttled to 10 Hz —
// not one event per crawled URL.
#[tauri::command]
async fn subscribe_progress(ch: Channel<CrawlProgress>)

Sorting and filtering become SQL against indexed columns, which SQLite does in milliseconds on millions of rows. Scroll position maps to OFFSET. Memory stays flat regardless of crawl size, and the app stays responsive mid-crawl because reads and writes are separated by WAL.

Crawl pipeline

Frontier (priority queue, deduped) → fetch pool (N workers, per-host rate limits) → parse (streaming, on a blocking thread pool) → batched writer (transactions of ~500 records) → audit rules (run incrementally, not at the end). Backpressure via bounded channels between each stage, so a slow disk throttles the fetchers instead of ballooning memory.

Politeness, non-negotiable

robots.txt honoured by default, per-host concurrency caps, configurable delay, honest identifiable user-agent with a URL to the project, and Retry-After respected. A fast crawler that gets its users IP-banned is a liability. Ship the safe defaults and make aggression opt-in and clearly labelled.

MVP — v0.1

Target: a crawl of 100k URLs, end to end, with a table you can actually work in. Roughly 10–14 weeks of solo evening work if the scope below holds.

It holds only if you treat the right-hand column as load-bearing. Every item there is something a competitor already has, and shipping none of them is the point.

In scope

  • +Crawl from a seed URL — depth, URL, and time limits
  • +robots.txt parsing, sitemap.xml discovery and ingestion
  • +Status codes, full redirect chains, response time, size, depth
  • +Internal vs external classification, nofollow handling
  • +Extraction: title, meta description, H1/H2, canonical, meta robots, hreflang, Open Graph, word count, images + alt
  • +Inlink / outlink graph per URL
  • +~30 audit rules covering the checks people actually open a crawler for
  • +Virtualised table: sort, filter, column picker, detail pane
  • +Issue overview with counts, drilling into a filtered table
  • +CSV + JSON export
  • +Save, close, reopen, resume a crawl
  • +Signed builds for all three platforms
  • +Published benchmark, reproducible by anyone

Explicitly not in v0.1

  • −JavaScript rendering
  • −Google Search Console / GA4 / third-party API integrations
  • −Scheduled or recurring crawls
  • −Link graph visualisation
  • −Custom extraction (CSS / XPath / regex)
  • −Crawl comparison and diffing
  • −PageSpeed / Core Web Vitals
  • −Log file analysis
  • −Structured data validation
  • −Spelling and grammar
  • −Auto-update
  • −Plugin system
08

Roadmap

Phases are sequential because each depends on the one before it — Phase 0 exists so that every later claim is measurable.

0.02 weeks

Benchmark harness first

A fixture site generator (axum) producing 100k pages with realistic link density, plus pathological cases: redirect loops, 30s responses, 5MB pages, malformed markup, robots edge cases. Criterion benches for parse throughput. A runner that measures URLs/sec, peak RSS, and wall time for Pounce and each competitor identically. Nothing else gets built until this works.

0.110–14 weeks

MVP — crawl, audit, table, export

The scope above. Ships with the first published benchmark and a README that names what's missing.

0.26 weeks

CLI and CI

pounce crawl --config pounce.toml --fail-on critical, JSON report output, meaningful exit codes, and a published GitHub Action. This is the "by developers, for developers" promise made real, and it's the thing no GUI-first competitor does well.

0.38 weeks

JavaScript rendering

chromiumoxide over CDP, as an opt-in per-crawl mode with its own concurrency budget. Detects installed Chrome rather than bundling one, so the binary stays small for the people who don't need it.

0.46 weeks

Custom extraction & crawl diffing

CSS/XPath/regex extractors, XML sitemap generation, and crawl-to-crawl comparison — "what changed since the last deploy" is the feature that turns a one-off audit tool into something opened weekly.

0.58 weeks

Integrations & scale

Search Console and GA4 joins, log file ingestion, link graph visualisation, and the push from 1M to 10M URLs per crawl.

1.0—

Rule SDK

Custom audit rules as WASM modules or embedded scripting. Developers writing and sharing their own checks is the endgame — it's the one thing that compounds, and it's where a free open tool beats a commercial one permanently.

10

Testing

  • Golden-file parser tests. A corpus of real-world HTML — including badly broken markup — with committed expected PageRecord output. Parser regressions are the highest-consequence bug class here, because they silently produce wrong audits.
  • The fixture site is the integration test. The same axum server built for benchmarking serves deterministic pathological cases. Crawl it, assert the exact resulting graph.
  • One test per audit rule. Every rule ships with a fixture that triggers it and one that doesn't. Non-negotiable — this is what keeps rule count from becoming rule debt.
  • Property tests on URL normalisation. Relative resolution, trailing slashes, case, ports, punycode, fragments, session IDs. This is where crawlers quietly break and loop forever.
  • Criterion benches in CI with regression thresholds. If throughput drops 10%, the build fails. When speed is the product, a perf regression is a broken build.
11

Project & community

Licence

Dual MIT / Apache-2.0 — the Rust ecosystem default. Apache-2.0 carries an explicit patent grant that makes corporate legal teams comfortable; MIT keeps it simple for everyone else. Contributors expect this pairing and it removes a whole category of friction.

Repository

Monorepo. README leading with the benchmark table and a "not yet implemented" section. CONTRIBUTING.md with a genuinely runnable dev setup. ARCHITECTURE.md explaining the query-don't-dump decision, because it's the thing every new contributor would otherwise get wrong. Conventional commits, release-please for changelogs, GitHub Actions matrix for the three platforms.

Sustainability

GitHub Sponsors, no paid tier, no telemetry, no account. Be explicit in the README that there will never be a paid tier — it is the single strongest trust signal you can send to an audience that has watched a dozen free dev tools get acquired and enshittified.

Distribution

GitHub Releases first. Then Homebrew, winget, Scoop, AUR, and a cargo install pounce-cli path. Developers install via package managers; being absent from them costs more adoption than any missing feature.

13

Next three actions

  1. Clear the name. crates.io, GitHub org, npm, and the domain. One hour, and it unblocks everything else.
  2. Build the fixture site and benchmark runner. Before any crawler code. If the numbers don't come out ahead on a synthetic 100k-page site, the entire premise is wrong and you'll have learned it in two weeks instead of six months.
  3. Spike the storage layer. Seed SQLite with a million synthetic rows and prove sort-and-filter round trips under 150ms through a real Tauri command. This is the load-bearing assumption in the whole architecture.
The honest version

You're entering a category with three free incumbents, one of which is well ahead on features. The plan above wins only if the performance gap is real and visible, and it stays winnable only if the scope stays brutally narrow. Phase 0 exists to tell you the truth cheaply — build it first, and let the numbers decide whether to continue.
